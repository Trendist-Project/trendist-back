# Trendist 3부. 운영

> 문서 목록과 변경 이력은 [docs/README.md](README.md). 절 번호(1~17)는 네 문서에 걸쳐 이어지고, 코드 주석의 `(4.8)` 같은 번호가 이 번호다.

## 13. 관리자 기능
관리자 화면은 React, API는 `ROLE_ADMIN` 전용이다. 관리자가 직접 운영한다.

### 13.1 키워드 금지
- 금지·해제만 하고 금지한 사람·사유·이력은 남기지 않는다. 금지 시각만 `keywords.banned_at`에 둔다.
- 금지 효과는 4.7.
- 신고된 키워드는 검토 목록에 올라오고 관리자가 판단한다. 신고 수에 따른 자동 조치는 없다.

### 13.2 소스 가중치
- 소스별 가중치(0~2)를 바꾼다. 0으로 두면 그 소스를 쓰지 않는다. 변경 이력은 남기지 않는다(키워드 금지와 같은 방식, 13.1).
- 저장하면 그 소스를 반영 소스로 쓰는 키워드의 `trend_value`를 바로 다시 계산하고, 보유자의 점수는 접속 중이면 바로, 아니면 다음 재합산(최대 1분)에 반영된다. 외부 확인과 반영 소스 선택은 다음 수집(매일 04:00)부터 새 가중치를 따른다.
- 크기가 바로 바뀌므로 저장 전에 영향받는 키워드·사용자 수를 보여 준다. 바꾼 직후 하루 동안(`data_sources.updated_at` 기준)은 💤 전환을 보류한다.
- 외부 API가 막히면 그 소스의 가중치를 0으로 한다(그 나라의 키워드는 외부 확인 없이 internal 점수로만 계산된다).

### 13.3 밸런스 설정
`settings`에 두고 배포 없이 바꾼다. 사유와 이력(`setting_histories`), 되돌리기, 허용 범위 검사가 있다. 1분 캐시 후 반영되고, 크기에 영향을 주는 값은 저장 전에 경고한다. 점수는 실시간 합이라 점수 관련 값을 바꾸면 모두의 크기가 바뀐다. 이미 받은 EXP는 다시 계산하지 않는다. 모든 나라 공통이다.

### 13.4 콘텐츠 관리
- 칭호: 이름·설명(한글)·아이콘·조건(`condition_type`·`condition_params`, 4.10)·순서·사용 여부를 추가·수정한다. 기준을 바꿔도 이미 준 칭호는 회수하지 않는다.
- 레벨: `levels`의 레벨별 누적 EXP를 보고 수정한다. 1레벨은 0이고, 1~100레벨이 빠짐없이 있어야 하며, 레벨이 오를수록 값이 커져야 한다(엄격 증가). 저장하면 모든 플레이어의 레벨을 다시 계산한다(배치, 저장 전에 레벨이 바뀌는 사용자 수를 보여 준다). 이미 장착한 꾸미기는 유지하고 변경만 새 레벨 기준으로 제한한다. 변경 이력은 남기지 않는다.
- 꾸미기: 프리셋 색 24색은 설정(코드)으로 관리하고 관리자 화면에서 바꾸지 않는다(2차).
- 공지·가이드 작성(4.16, 4.17), 금지 닉네임·차단어 등록.

### 13.5 신고와 이미지 검열
- 신고 대상: 키워드, 댓글, 아이콘 이미지, 플레이어, 채팅(유형은 `report_types`). 신고는 신고한 플레이어가 기록되어 어느 나라에서 신고했는지 알 수 있고, 계정은 플레이어를 통해 찾는다(제재는 계정 단위, 아래 사용자 제재). 한 플레이어가 같은 대상을 한 번만 신고한다. 모든 신고는 관리자 검토로 처리하고 자동 조치는 없다. 신고하면 대상의 `report_count`를 1 올린다(댓글·채팅). 지금은 댓글과 채팅 신고만 받고(`POST /api/reports`), 관리자 검토 화면은 아직 없다.
- 이미지 자동 검열
  - 경량 NSFW 모델(GantMan/nsfw_model 또는 Yahoo open_nsfw)을 ONNX로 돌려 높으면 거부, 애매하면 저장 후 검토 목록. 선정성만 보므로 나머지는 신고와 사용자 제재로 대응한다.
  - 모델을 쓸 수 없거나 실패하면 거부하지 않고 검토 목록에 올린다.
  - 위반 이미지의 지각 해시(pHash)로 다시 올리는 것을 막는 기능은 2차다(5.1).
- 사용자 제재: 관리자가 계정 금지, 이미지 업로드 정지, 댓글 작성 정지를 걸 수 있다(종류는 `sanction_types`). 반복 위반이면 걸고, 걸 때마다 사유와 기간을 `sanctions`에 남긴다. 기간은 제재 타입의 일수(`sanction_types.day`)로 정해 만료 예정 시각(`expires_at`)에 넣고, `day`가 비어 있으면 영구 제재라서 `9999-12-31 23:59:59`로 둔다. 만료 전에 관리자가 풀면 실제로 푼 시각(`released_at`)을 기록한다. 제재 중인지는 `released_at`이 없고 `expires_at`이 지금보다 뒤인지로 판단한다.
- 현재 상태는 빠르게 확인하려고 `users`에도 둔다: 계정 금지는 `banned_until`, 이미지 업로드 정지는 `upload_banned_until`. NULL이면 제재 없음, 지금보다 뒤 시각이면 제재 중이다. 만료는 시각 비교로 자동이라 따로 잡이 필요 없다. 제재를 걸거나 풀 때 `sanctions`와 `users`를 한 트랜잭션에서 같이 고친다. 댓글 작성 정지는 댓글을 쓸 때만 확인하므로 `sanctions`에서 직접 조회한다.
- 금지된 계정은 입장할 수 없고 접속 중이면 연결을 끊는다. 게스트는 쿠키를 지우면 새 방문자 ID를 받아 금지를 피할 수 있으므로, 로그인한 계정만 확실히 막을 수 있다.
- 삭제·탈퇴한 댓글 원문은 신고·법적 요청 대응 때만 열람한다.

### 13.6 트렌드 키워드 목록
관리자만 보는 조회 화면이다(`ROLE_ADMIN`). 일반 사용자에게는 보이지 않으므로 3.3의 비노출 원칙과 충돌하지 않는다. 나라를 고르면 그 나라 키워드를 보여 준다.

- 열: 키워드, 상태, 트렌드 값, 반영 소스, 가진 사람 수, 누적 `+` 수, 누적 검색 수, 최근 24시간 검색 수·`+` 수(`keyword_log_24h` 증분 합), 🔥가 된 날.
- 필터: 상태, 반영 소스, 키워드 검색어, "반영 소스가 internal(사람만으로 활성)"만 보기. 정렬: 트렌드 값 / 가진 사람 수 / 누적 `+` 수 / 최근 24시간 검색 수. 한 페이지 50개.
- 소스별 관심도 값은 저장하지 않으므로 보여 주지 않는다(10.2).
- 행을 열면 일반 카드와 같은 활동 그래프(4.12)를 보여 주고, 거기서 바로 금지·해제할 수 있다(13.1).
- 조회 전용이고 결과는 1분 캐시한다. 내보내기(CSV)는 2차다.

## 14. 안전과 남용 방지

| 위험 | 대응 |
|---|---|
| 클라이언트 조작 | 서버 권위 시뮬레이션, 클라이언트는 입력만 전송, 목표 지점 서버 보정 |
| `+` 매크로·선점 쌓기 | 같은 키워드 1회, 24시간 삭제, 🔥활성 키워드만 점수(💤 0점), 요청 빈도 제한 |
| 임의 단어를 `+`해서 EXP·레벨 올리기 | 같은 키워드 24시간 1회, 새 키워드 생성 분당 제한(9.5), EXP 점수 반영 상한 100, 베타에서 레벨 분포 점검 |
| 새 키워드 스팸·담합 | IP 제한, 형식 검사, 💤 키워드 0점, 사람만으로 활성된 키워드는 3명부터 시작·반영값 1·완만한 증가, 신고 |
| 특정인 비방·개인정보 | 실존 인물 이름·URL·전화번호·이메일 패턴 차단, 신고 후 삭제 |
| 민감 키워드 | 차단어 목록, 관리자 금지 |
| 방문자 ID 탈취·위조 | 서버 발급 UUID v4, HttpOnly·Secure 쿠키, 다른 사용자에게 비노출 |
| 토큰 탈취·재사용 | 액세스 15분, 갱신 토큰은 HttpOnly 쿠키·회전·재사용 감지, 금지·탈퇴·로그아웃 때 폐기 |

| 충돌로 키워드 털기(괴롭힘) | 잃은 뒤 3초 무적(모두에게 카운트다운 표시)·입장 직후 10초 보호 |
| 트렌드 상자 키워드 유출·원격 열기 | 키워드는 연 사람에게만 개별 전송, 서버 위치로 거리 검사, 한 사람 한 번 |

| 24시간 주기의 피로·이탈(며칠 쉬면 최소 크기) | 재방문율을 보고 삭제 시간 조정. EXP 점수 100은 남는다 |
| 외부 값이 하루 1번만 갱신되어 외부 확인 여부가 하루 단위로만 바뀜 | 하루 중 점수 변화는 가진 사람 수가 맡는다. 기본 비율과 반영값을 베타에서 점검 |
| 새 키워드가 24시간 안에 3명을 못 모음 | 🔥활성 전환 인원과 사람만 키워드의 반영값 조정 |
| 이미 붐비는 키워드를 따라 하는 `+`가 유리해짐(몰려가기) | 로그-선형 곡선과 1,000명 상한으로 이득을 제한, 소셜 학습 경로로 허용 |
| 04:00 수집으로 반영 소스가 한꺼번에 바뀌어 점수가 출렁임 | 크기 변화 0.5초 보간, 점수 변경 알림으로 이유를 보여 줌 |
| 인기 키워드에 `+`가 몰리면 보유자 점수·크기 갱신이 폭주 | 틱마다 변화량을 합쳐 한 번만 계산, 갱신은 스냅샷 주기가 상한, DB 저장은 5초마다 모아서 |
| 1000명 방 부하(방 송신 초당 약 9MB 추정) | 관심 영역, 공간 격자, 부하 테스트 후 스냅샷 주기(15→10Hz)나 상한 조정 |
| 큰 아이콘(최대 지름 1,200px)이 화면·통로를 막고 관심 영역이 넓어져 송신량 증가 | 줌아웃, 관심 영역 엔티티 상한, S_cap과 최대 지름 비율을 베타에서 조정 |
| 1000명 상한에 막힘 | 상한 도달 모니터링, 방 확장 |
| 충돌로 키워드를 잃는 규칙 때문에 작은 사용자가 이탈 | 보호 시간 조정, 베타에서 잃은 횟수와 이탈률 점검 |
| 트렌드 상자 키워드를 채팅으로 퍼뜨려 모두가 따라 `+` | 공개 시간이 짧고 상자 키워드는 이미 외부에서 확인된 키워드라 이득이 작다. 사람끼리 공유는 허용 |
| 키워드가 적은 초기에는 상자 후보가 없음 | 후보가 없으면 생성하지 않음. 필요하면 최소 트렌드 값을 낮춤 |
| 레벨 곡선(1~100)이 실제 `+` 속도와 맞지 않음 | 베타에서 레벨 분포를 보고 `levels`를 조정 |
| 가중치·밸런스 변경으로 크기가 한꺼번에 바뀜 | 저장 전 경고, 되돌리기, 큰 변경은 공지 |
| 댓글이 비어 있음, 틀린 댓글이 상위 | 빈 상태 안내, 운영자 첫 댓글, "사실 확인 안 됨" 라벨, 신고 |

| 다국어 운영·번역 부담 | 기계 번역 + 원어민 검수, 언어별 검토 인력 |
| 금지 기준 불만 | 이용약관에 기준 공개 |

## 16. 열린 쟁점과 확인 필요

### 16.1 결정 필요
- 운영 DB의 스키마 반영 방식: 개발·테스트는 JPA 자동 반영(11.3)이다. 출시 전에 17절 SQL(`4-schema.sql`)을 기준으로 Flyway 마이그레이션으로 전환하는 시점과 방법을 정한다.
- 그 밖에 정해야 할 항목은 없다. 보류한 아이디어는 5.2에 있다.

### 16.2 확인 필요
- 데이터: 네이버 데이터랩 호출 한도(하루 1,000회 확인)·약관, BigQuery 국제 데이터셋이 하루 중 언제 갱신되는지(04:00 배치 때 그날 값이 이미 있는지)와 네이버 데이터랩의 최신 날짜 반영 지연, 원본 재배포 약관, BigQuery 지원 국가, 네이버 앵커 보정 방식 검증, 구글 트렌드 실시간 인기 RSS의 상업적 이용 가능 여부와 주소·형식 유지 여부, 실시간 인기 제목에 실존 인물 이름이 많아 4.6 실존 인물 패턴 검사가 필요한지
